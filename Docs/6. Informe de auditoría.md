## 1. HALLAZGOS CRÍTICOS (11)

### 1.1 Seguridad

#### C1 — Endpoint `/shutdown` sin protección
**Ubicación:** `src/main/java/com/odontologia/formatos/controller/Main.java:49-52`

Cualquier persona o script puede detener el servidor sin autenticación:

```java
app.post("/shutdown", ctx -> {
    ctx.json(Map.of("status", "shutting_down"));
    app.stop();
});
```

**Riesgo:** Denegación de servicio remota.
**Solución:** Eliminar en producción o proteger con autenticación.

---

#### C2 — CORS configurado con `anyHost()`
**Ubicación:** `src/main/java/com/odontologia/formatos/controller/Main.java:27`

```java
cors.addRule(it -> {
    it.anyHost();
    it.allowCredentials = false;
});
```

**Riesgo:** Cualquier dominio puede consumir la API. Vulnerable a CSRF y ataques cross-origin.
**Solución:** Configurar orígenes específicos (e.g. `http://localhost:5173` en dev, `file://` en producción Electron).

---

#### C3 — `webSecurity: false` en Electron
**Ubicación:** `frontend/electron/main.ts:89`

Deshabilita la same-origin policy del renderer. Permite que cualquier script haga requests cross-origin sin restricciones.

**Riesgo:** Vulnerabilidad de seguridad en producción.
**Solución:** Remover `webSecurity: false` o restringir a las URLs necesarias mediante `ses.webRequest`.

---

#### C4 — Sin autenticación ni autorización
**Ubicación:** `src/main/java/com/odontologia/formatos/controller/Main.java:23-31`

No existe ningún mecanismo de autenticación (JWT, Basic Auth, API keys, sesiones). Todos los endpoints son públicos. Las anulaciones registran `Usuario = "SYSTEM"` hardcodeado en `RegistroAnulacionRepository.java:21-22`.

**Riesgo:** Cualquier proceso con acceso a localhost:7070 puede operar el sistema completo.
**Solución:** Implementar al menos Basic Auth + API key para el entorno local, o JWT si se expone en red.

### 1.2 Integridad de datos

#### C5 — `TransaccionBD` no revierte ante `NegocioException`
**Ubicación:** `src/main/java/com/odontologia/formatos/util/TransaccionBD.java:28-57`

```java
con.setAutoCommit(false);
try {
    operacion.ejecutar(con);   // Si lanza NegocioException (RuntimeException)...
    con.commit();
} catch (SQLException e) {     // NO se captura aquí
    con.rollback();
    throw e;
} finally {
    con.setAutoCommit(true);   // En SQLite, restaurar auto-commit puede COMMITEAR la transacción pendiente
}
```

Cuando `NegocioException` (RuntimeException) se lanza dentro del lambda, el bloque `catch(SQLException)` no la captura. El `finally` restaura `autoCommit=true`, y en SQLite JDBC esto puede comitear implícitamente la transacción parcial, dejando la base de datos en estado inconsistente.

**Riesgo:** Corrupción de datos ante errores de negocio dentro de transacciones.
**Solución:** Agregar `catch(RuntimeException e) { con.rollback(); throw e; }` además del catch de SQLException.

#### C6 — 8 fugas de conexiones JDBC
**Ubicación:**

| Archivo | Método | Líneas |
|---|---|---|
| `repository/AsistenciaRepository.java` | `anular(Connection con, ...)` | 73-80 |
| `repository/AsistenciaRepository.java` | `registrarEntrada(Connection con, ...)` | 82-90 |
| `repository/AsistenciaRepository.java` | `registrarSalida(Connection con, ...)` | 92-100 |
| `repository/AsistenciaMaterialRepository.java` | `delete(Connection con, ...)` | 65-77 |
| `repository/AsistenciaMaterialRepository.java` | `deleteByAsistenciaID(Connection con, ...)` | 83-95 |
| `repository/PeriodoAusenciaRepository.java` | `finalizar(Connection con, ...)` | 42-55 |
| `repository/PeriodoAusenciaRepository.java` | `delete(Connection con, ...)` | 61-73 |
| `repository/TratamientoMaterialRepository.java` | `deleteByTratamientoID(Connection con, ...)` | 79-91 |

Estos métodos aceptan un parámetro `Connection con` que puede ser `null`. Cuando es `null`, abren una nueva conexión que nunca se cierra.

**Nota:** En el uso actual, estos métodos siempre se llaman con `con != null` desde los servicios (vía `TransaccionBD`), por lo que el bug no se manifiesta en producción actual. Sin embargo, el código es frágil — cualquier llamada futura con `con == null` producirá una fuga.

**Solución:** Agregar bloque `finally { if (cerrarConexion) conexion.close(); }` como ya se hace en otros métodos del mismo repositorio.

### 1.4 Frontend crítico

#### C9 — Sin ErrorBoundary
**Ubicación:** `frontend/src/App.tsx:11`

No existe ningún componente de ErrorBoundary en toda la aplicación. Si cualquier componente lanza una excepción no controlada durante el renderizado, toda la UI se rompe con una pantalla en blanco en Electron.

**Solución:** Crear `src/components/ErrorBoundary.tsx` e instalarlo como wrapper en `App.tsx` alrededor de `<Routes>`:

```tsx
<HashRouter>
  <ToastProvider>
    <ErrorBoundary>
      <Routes>...</Routes>
    </ErrorBoundary>
  </ToastProvider>
</HashRouter>
```

---

#### C10 — Bug en `useApi`: `fetcher` fuera del array de dependencias
**Ubicación:** `frontend/src/hooks/useApi.ts:35`

```typescript
const execute = useCallback(async () => { ... }, deps);
```

El array `deps` no incluye `fetcher`. Si el `fetcher` cambia (porque es una arrow function recreada en cada render), `execute` usará la referencia vieja del closure.

**Riesgo:** Llamadas API con parámetros obsoletos.
**Solución:** Incluir `fetcher` en el array de dependencias o memoizarlo con `useCallback`.

---

#### C11 — `preload.ts` expone 180 líneas de API muerta
**Ubicación:** `frontend/electron/preload.ts:18-186`

El archivo `preload.ts` expone toda la API HTTP (~180 líneas) al renderer vía `contextBridge`. Sin embargo, **nunca se usa** desde el frontend. El único método utilizado es `window.api.shell.openPath` en `Reportes.tsx:33`.

**Riesgo:** Superficie de ataque innecesaria expuesta al proceso renderer.
**Solución:** Eliminar todo el API client del preload y dejar solo `shell.openPath`.

## 2. HALLAZGOS ALTOS (27)

### 2.1 Backend — Condiciones de carrera

#### A1 — `AsistenciaService`: TOCTOU en 5 métodos
**Ubicación:** `service/AsistenciaService.java:54-203`

En los métodos `registrarEntrada`, `registrarSalida`, `iniciarAusencia`, `finalizarAusencia`, `eliminarAusencia` y `anular`, se hace `findById()` fuera de la transacción y luego se opera dentro de `TransaccionBD.ejecutar(...)`. Entre ambas operaciones, otro hilo podría modificar el registro.

**Solución:** Mover `findById()` dentro de la transacción.

---

#### A2 — `TratamientoService.cerrar()`: doble lectura y validación inconsistente
**Ubicación:** `service/TratamientoService.java:163-171`

```java
public void cerrar(int tratamientoID) throws SQLException {
    validarAbierto(tratamientoID);     // findById() fuera de transacción
    TransaccionBD.ejecutar(con -> {
        Tratamiento t = repository.findById(tratamientoID);  // segunda lectura
        t.setEstado("CERRADO");
        repository.update(con, t);
    });
}
```

La primera validación lee la entidad fuera de la transacción. La segunda lectura dentro de la transacción podría obtener un estado diferente.

**Solución:** Hacer la validación dentro de la transacción.

---

#### A3 — `TratamientoService.reabrir()`: sin transacción
**Ubicación:** `service/TratamientoService.java:198-212`

El método no usa `TransaccionBD.ejecutar`. La validación `existeOtroAbiertoEnUnidad` y el `update` son operaciones separadas.

**Solución:** Envolver en `TransaccionBD.ejecutar`.

---

#### A4 — `UnidadService.eliminar()`: check-then-act sin transacción
**Ubicación:** `service/UnidadService.java:23-29`

```java
if (tieneTratamientoAbierto(unidadID)) { throw ... }
repository.delete(unidadID);
```

Entre la verificación y el borrado, un tratamiento abierto podría iniciarse en la unidad.

**Solución:** Envolver en transacción.

---

#### A5 — `UnidadService.crear()`: race condition en auto-incremento manual
**Ubicación:** `service/UnidadService.java:16-18`

```java
int siguienteNro = repository.maxUnidadNro() + 1;
```

Dos peticiones concurrentes pueden obtener el mismo `maxUnidadNro` y crear unidades con el mismo número.

**Solución:** Usar `INSERT ... SELECT MAX(UnidadNro) + 1 FROM Unidad` dentro de una transacción, o usar un constraint UNIQUE en UnidadNro.

### 2.2 Backend — Validación y errores

#### A6 — Validación de inputs insuficiente
**Ubicación:** `controller/AsistenciaController.java:32-34`, `controller/TratamientoController.java:41-51`

No se valida que los campos obligatorios del body JSON estén presentes antes del cast. Si falta `docenteId` o `fecha` en el body de asistencia, se produce un `NullPointerException` que resulta en HTTP 500 con mensaje genérico.

**Solución:** Validar existencia de campos requeridos al inicio de cada handler y retornar 400 con mensaje descriptivo.

---

#### A7 — Path params sin validación de formato
**Ubicación:** `controller/AsistenciaController.java`, `controller/CatalogoController.java`, `controller/TratamientoController.java`, `controller/UnidadController.java` (~50 endpoints)

`Integer.parseInt(ctx.pathParam("id"))` no captura `NumberFormatException`. Si llega `/api/tratamientos/abc/materiales`, el servidor devuelve 500.

**Solución:** Capturar `NumberFormatException` y retornar 400 Bad Request.

---

#### A8 — PUT de catálogos sin `estado` en body desactiva entidades accidentalmente
**Ubicación:** `model/Docente.java:9`, `model/Operador.java:12`, `model/Materiales.java:8`, `model/Paciente.java:7`, `model/TratamientoPredefinido.java:8`

Los campos `estado` son `int` (primitivo) con valor por defecto `0`. Cuando el frontend envía un PUT como `{"nombres":"Nuevo","apellidos":"Nombre"}` sin incluir `estado`, Jackson lo deserializa con `estado = 0`, y el repositorio persiste `Estado = 0`, desactivando la entidad.

**Afecta:** `CatalogoController.java:58-64` (Operador), `92-98` (Docente), `125-131` (Paciente), `168-174` (Materiales).

**Solución:** Usar `Integer` (wrapper) con inicialización a `null`, o usar DTOs separados para requests de creación/actualización.

---

#### A9 — Modelos sin Jakarta Bean Validation
**Ubicación:** Los 14 modelos en `src/main/java/com/odontologia/formatos/model/`

Ningún modelo tiene anotaciones como `@NotNull`, `@NotBlank`, `@Size`, `@Positive`, `@Min`, `@Max`. La validación se hace manualmente en los servicios.

**Solución:** Agregar dependencia `jakarta.validation:jakarta.validation-api` e implementación `hibernate-validator`, y anotar los modelos.

---

#### A10 — Handler global imprime stack traces en `stderr`
**Ubicación:** `controller/Main.java:41-44`

```java
app.exception(Exception.class, (e, ctx) -> {
    System.err.println("Error no manejado: " + e.getMessage());
    e.printStackTrace();
```

En producción, los stack traces no deberían imprimirse en stderr.

**Solución:** Usar el logger configurado (SLF4J) con nivel adecuado según entorno.

#### A19 — API client sin timeout, retry ni AbortController
**Ubicación:** `api/index.ts:46-61`

- **Sin retry:** Errores de red transitorios no se reintentan.
- **Sin interceptor global:** Errores 401/403/500 se manejan caso por caso.
